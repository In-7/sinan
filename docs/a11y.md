# 无障碍（a11y）

无障碍是"能不能被用"的问题，不是打磨项。本文记基线、官方检查器的用法与局限、以及
两处需要决策的边界。**跑法**：`flutter test test/a11y/`（报告打在 stdout）。

## 一、基线（2026-09-17 实测；画布的守卫口径 2026-09-18 修正）

| 界面 | 有标签部件 / Text 部件 | 标签 | 对比度 | 24×24 |
|---|---|---|---|---|
| 笔记列表 | 2 / 2 | ✅ 门槛 | ✅ 门槛 | ✅ 门槛 |
| 自绘标题栏 | 1 / 1 | ✅ 门槛 | ✅ 门槛 | ✅ 门槛 |
| 块编辑器 | 4 / 3 | ✅ 门槛 | ✅ 门槛 | ✅ 门槛 |
| 画布（整页） | 1 / 1（工具栏缩放百分比按钮） | ✅ 门槛 | ✅ 门槛 | ✅ 门槛 |
| ↳ 画布**内容** | **0 / 0** | 🕳 **盲区**（✅ 是假阴性） | — | — |

三类断言的分工（`test/a11y/accessibility_test.dart`，别混用）：

| 类别 | 形态 | 含义 |
|---|---|---|
| **硬门槛** | `expect(..., isTrue)` | 现在就是绿的，**不许退回去** |
| **账本** | `skip: true` + 理由写进**用例名** | 已知欠账：可见、不假装绿、也不拦 CI；修好只需删掉 `skip` |
| **盲区守卫** | `expect(画布内容语义规模, findsNothing)` | 画布**内容**零语义节点 ⇒ 检查器在它身上全绿是**假阴性**；一旦非空就要求同步改文档。⚠️ **范围是 `CanvasView` 子树，不是整页**——工具栏 chrome（缩放百分比按钮等）是真正的交互件，本该有语义与 tooltip |

> 守卫为什么按子树而不是整页（2026-09-18）：曾用"整页语义节点 == 0"当守卫，随后
> 工具栏加了缩放百分比按钮（一个 `TextButton` + `Tooltip`）就把守卫顶红了 —— 而它
> 盯的"内容是零语义"这个事实仍然成立。按整页计数会让**加任何 chrome 都触发假警报**，
> 真正的盲区反而没人守。

## 二、官方三个检查器（已核到源码）

```dart
labeledTapTargetGuideline        // accessibility.dart:825（LabeledTapTargetGuideline）
textContrastGuideline            // :818（MinimumTextContrastGuideline）
MinimumTapTargetGuideline(size:, link:)   // :116，构造函数需 size + link
```

四条**必须知道**的事实：

1. **`tooltip` 也算合格标签**——判据是 `if (label.isEmpty && tooltip.isEmpty)`（`accessibility.dart` 第 264 行）。所以已有的 `Tooltip` 大多本就合格。
2. `evaluate()` 直接读 `semanticsOwner.rootSemanticsNode` ⇒ 测试里**必须先 `tester.ensureSemantics()`**。
3. 官方**只有** `androidTapTargetGuideline`(48×48) 与 `iOSTapTargetGuideline`(44×44)，**没有 Windows 预设**。桌面按 **WCAG 2.2 SC 2.5.8 = 24×24**，用 `MinimumTapTargetGuideline(size: Size(24, 24), link: ...)` 自定义。
4. ⚠️ **检查器的局限**：它们只遍历**已存在**的语义节点。自绘界面（画布）不产出节点 ⇒ 全绿。**"全绿"必须读作"没有可查的东西"，不能读作"合格"。**

## 三、已修：tooltip 的归属（2026-09-17）

`_HistoryButton`（撤销/重做）与 `_EarButton`（搜索/目录）原来写成 **外层 `Tooltip` 包 `IconButton`**：

```dart
Tooltip(message: '撤销（Ctrl+Z）', child: IconButton(onPressed: ..., icon: ...))
```

`Tooltip` 会把提示挂在**父语义节点**上，按钮自己那个节点仍然没有名字——读屏（NVDA）念出来
只是"按钮"。改成把 tooltip 交给按钮自己后，编辑器的标签违规 **3 → 2**：

```dart
IconButton(tooltip: '撤销（Ctrl+Z）', onPressed: ..., icon: ...)
```

**规则**：图标按钮一律 `IconButton(tooltip: ...)`；**不要**在外面包 `Tooltip`。
自绘的、非按钮的可点区域则显式写 `Semantics(label: ..., button: true)`。

**同一主题的第二条规则（2026-09-17 同日踩到）**：**无文字的可点区**（点空白聚焦、
拖拽空白之类）若**不打算给读屏用**，就显式写 `excludeFromSemantics: true`。
否则它的 `tap` 会**向上合并进最近的一层语义边界**（编辑器里就是滚动视口），
表现为"那个边界变成一个没有名字的可点目标"——排查时**极易误判成 vendored 的锅**
（本次实际误判过一次）。若确实想让读屏用户也能用，正确做法是给一个**有名字**的
元素（如工具栏按钮），而不是让一片无名区域可点。已应用于编辑器 `footer`
（`note_editor_view_appflowy.dart`）。

> 这条是靠 a11y 盘点发现的：**视觉上完全看不出来**（hover 提示照常有），只有读屏那一路缺名字。

## 五、决策：vendored 的视口/正文节点——**打补丁**（不是包 `Semantics`）

现象（`test/a11y/` 报出，明暗各一次）：

```
SemanticsNode#10(Rect 0,34→800,511, tags:[RenderViewport.twoPane], actions:[tap])  // 滚动视口
SemanticsNode#8 (Rect 0,57→800,568, actions:[focus,tap], flags:[isFocused])          // 正文容器
```

两条都在 `third_party/appflowy_editor` 的编辑器根上（我们的 `_MetaBar` 那 3 个按钮修完已不再报）。

**外部包装做不到精确修复**——能用的手段只有三种，全都不对：

| 手段 | 后果 |
|---|---|
| `Semantics(label: '正文')` | 不设 `container` 时标签会并到相邻节点，归属不确定，检查器不一定认 |
| `Semantics(container: true, label: ...)` | **把子树语义压进一层**，读屏失去逐块/逐行导航——看起来修了，实际更糟 |
| `ExcludeSemantics` | 整棵子树语义全丢（灾难） |

即：**外部只能"加"、不能"减"**，也无法精确指定"给哪一个节点补名字"。

**打补丁**则能改到点子上，且本仓库**已有成熟补丁流程**（`third_party/appflowy_editor/PATCHES.md`，
已 16+ 个补丁，最近一个就在改 `_onSecondaryTapDown`）⇒ 边际成本低，升级反正是要重打的。

稳定性对比：补丁的风险是"升级冲突"（可预期、有流程）；包 `Semantics` 的风险是
"**悄悄破坏内部语义**"（不可预期、没有测试能发现）。**前者更稳定。**

优先级：① 我们自己的（已完成）② vendored 打补丁（小）③ 画布补语义（大）。

**已落地（2026-09-17，`PATCHES.md` 补丁 17）**：`selection_gesture.dart` 的
`RawGestureDetector` 加 `excludeFromSemantics: true` —— 只让**手势层**不贡献语义
（`_GestureSemantics` 完全不挂），子节点语义不受影响。效果 **2 → 1**：
"文档容器"那条（`actions: [focus, tap]`，选择手势与焦点节点合并而成）被清掉，
**证明了这个判断**——一行 `excludeFromSemantics` 就精确删掉了本层动作，而外围包
`Semantics` 做不到这一点。

**最后 1 条"滚动视口"经查明与 vendored 无关**（同日）：是应用侧 `footer` 的 `tap`
向上**合并**到视口节点造成的，已由应用侧 `excludeFromSemantics` 修掉——详见 §4 #1 与
§3 的第二条规则。至此四个界面的"标签"项**全部达标**（画布除外，它没有节点可查）。

## 六、两条"不能当真"的边界

1. **生产底色不可完全复现**：测试进程没有平台窗口合成，只能用
   `AppTheme.windowBackground/contentCanvas` 近似 ⇒ 对比度的数字**只有参考价值**，最终要人眼复核。
   - ~~**决策（2026-09-17，用户定）：不为高对比度模式另做不透底背景。**~~ **已作废（2026-10-07）**：
     窗口材质（Mica 等）已整体取消（见 `docs/ui_rewrite_plan.md` §5.6），底色是我们自己的
     **不透明令牌色** ⇒ 系统开**高对比度（HC）模式**时不再有"系统撤掉 DWM 背景"这件事，
     底与对比度都归我们控制（也无需 `MediaQuery.highContrastOf`）。
2. **尺寸门槛是桌面口径（24×24）**，不是官方预设的 48：我们最小窗宽 720、属高密度桌面 UI，48 会大面积误报。是否按触屏笔记本提到 32–40 见 §4 #3。

## 七、与官方对照

官方《无障碍》页给的是一条**发布前自查清单**：对比度 ≥ 4.5:1、点击目标尺寸、文本缩放、
色觉辨认、屏幕阅读器、错误可撤销。我们逐条的状态：

| 官方条目 | 状态 |
|---|---|
| 对比度 | 🟡 检查器在测试环境通过，实机仍需人眼复核 |
| 点击目标 | ✅ 桌面口径已锁门槛；触屏门槛待决策 |
| 文本缩放 | ✅ 已处理（`MediaQuery.textScalerOf` + 块高预算器把 `textScaleFactor` 算进尺寸） |
| 色觉辨认 | ❌ 未做：墨色/高亮/待办状态大量**只用颜色**区分，缺形状或图标冗余 |
| 屏幕阅读器 | 🟡 列表/标题栏/编辑器已合格；**画布完全不可读**（盲区，见 §1） |
| 错误可撤销 | ✅ `undo_toast` + 画布命令栈 |
