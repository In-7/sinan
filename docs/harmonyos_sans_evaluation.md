# HarmonyOS Sans 内置评估（2026-09-10）

- 动机：`docs/editor_migration_spike.md` 的「排版基准」已把字号/字重对齐到 Apple × 鸿蒙
  共识，**唯一没对齐的是字体族**（我们用系统雅黑/苹方，鸿蒙用 HarmonyOS Sans）。
- 评估范围：体积 · 中英基线 · 与现有 CJK 回退链的关系 · **许可**（本次出现阻断项）。

## 结论速览

| 维度 | 结论 |
|---|---|
| **许可** | ⛔ **阻断**：三条公开渠道都拿不到可信条款（§4）⇒ **法务确认前不内置** |
| **体积** | ⚠️ 结构确定、单值需实测：**中文字体不可子集化** + Flutter **不支持 woff2**，我们只需 2 个字重 ⇒ 增量 ≈ 2 × 单字重全量体积（§2） |
| **中英基线** | ✅ **无回归**：HarmonyOS Sans 自带配套 Latin，与今天"雅黑自带拉丁"同构（still 中英同源、基线恒定）（§3） |
| **与回退链** | ✅ 内置后回退链从"平台适配"转为"缺字兜底"，**必须保留**；另有一条**零风险软对齐**可立即做（§5） |
| **建议** | 立即做**软对齐**（把字体名放进回退链链首）；**内置等法务**（§7） |

## 1. 背景与动机

现状：`AppTheme.editorFont = 'Microsoft YaHei UI'` + `cjkFontFallback =
[Microsoft YaHei UI, PingFang SC, Noto Sans CJK SC]`（见 `lib/src/theme/app_theme.dart`）。

⇒ 两个已知短板：

1. **各平台渲染不同**（Windows 雅黑 / macOS 苹方 / Linux Noto），同一篇笔记换系统换观感；
2. Windows 上 `w600` 标题是否存在**真实 Semibold 面**不确定 —— Skia 会取最接近的字重
   （实测等效于 Bold，可用但不受控）。

内置 HarmonyOS Sans 的两个真收益：**三平台渲染一致** + **字重齐全**（Regular / Medium /
Semibold / Bold 都是真实字重，标题 `w600` 不再"取最近"）。

## 2. 体积

**可以确定的三条**（决定了量级）：

1. **中文字体不能子集化**：编辑器要支持用户输入任意汉字（含生僻字），按字符集裁剪会在
   生僻字上出现方框 ⇒ 必须全量打包；
2. **Flutter 的 asset 字体只吃 ttf/otf，不支持 woff2** ⇒ 用不了网页那套压缩；
3. 我们**只需要 2 个字重**：Regular（正文 `w400`）+ Semibold（标题 `w600`）。

⇒ **安装包增量 ≈ 2 × 单字重全量体积**（若能用可变字体 VF 压成 1 个文件则更省，但 Flutter
对 VF 的支持需另行验证）。

**需要实测才能定的数**（我在本地取不到，请按此法测）：

- 到华为开发者联盟「设计资源下载」取官方字体包 → 解压 → 看
  `HarmonyOS_Sans_SC_Regular.ttf` 的字节数；
- 旁证（公开字体站的字段，非官方）：`HarmonyOS Sans SC` 的**字符数 29,051** —— 说明这是
  一个**全量 CJK 字体**，不是子集包。

## 3. 中英基线影响

- HarmonyOS Sans **自带配套的 Latin 字形**（同一字族的西文设计），与我们今天的做法**同构**：
  今天用雅黑的中英同源来保证"同一行内基线恒定"（`note_editor_view.dart` 的
  `_chineseStyles` 注释里记过：中英各用一套字体时，升部/降部比例不同会让基线上下漂移）。
- ⇒ 换到 HarmonyOS Sans **不破坏这个性质** ✓，且它的 Latin 是专门配套设计的（观感优于
  雅黑自带的拉丁）。
- **改动面小**：`AppTheme.editorFont` 一个常量 + 回退链；**UI chrome 的 Segoe UI 不动**
  （编辑器与 chrome 有意分离，是既有约定）。
- **唯一风险**：Latin 字面宽度 / 行盒度量与雅黑略有差异 ⇒ **换行位置、行盒高度有微小变化**
  （无功能影响，属观感变化，需人眼过一遍）。

## 4. 许可（本次评估的阻断项）

| 渠道 | 情况 |
|---|---|
| 华为开发者联盟「设计资源下载」页 | 宣称免费商用，但**条款原文在 JS 渲染的页面里**，静态抓取拿不到 ✗ |
| GitHub `huawei-fonts/HarmonyOS-Sans` | 仓库 `LICENSE` = **GPL-3.0**，且**没有 font exception** ✗ —— 按 GPL，随应用分发需提供"对应源码"、整体沿用 GPL、不得附加限制；**嵌入专有应用有传染风险** ✗ |
| 同上仓库的字体包 | `HarmonyOS Sans.zip` 实测仅 **133 字节**（Git LFS 指针 / 占位 ✗），**不是真字体包** ⇒ 该仓库连体积也无法作为依据 |

⇒ **结论：在法务或华为官方条款原文确认之前，不内置**（我们是随应用分发的桌面软件，
这一条比体积更该先解决）。
⇒ 若将来确认可内置：需在第三方许可登记中写明**字体名称 / 来源 / 版本 / 许可全文副本**。

## 5. 与现有 CJK 回退链的关系

| | 现在 | 内置之后 |
|---|---|---|
| `fontFamily` | 系统字体（各平台不同） | `'HarmonyOS Sans SC'`（随包） |
| `fontFamilyFallback` 的角色 | **平台适配**（Win→雅黑 / mac→苹方 / Linux→Noto） | **缺字兜底**（生僻字、emoji、其它语言）⇒ **必须保留**，不能因为"内置了"就删 |
| 跨平台一致性 | ✗ 平台间不同 | ✓ 一致 |

### 立即可做的"软对齐"（零体积、零许可风险）

把字体名放进**回退链链首**：

```dart
// lib/src/theme/app_theme.dart
static const List<String> cjkFontFallback = <String>[
  'HarmonyOS Sans SC',   // 装了鸿蒙字体的用户（设计师 / 鸿蒙用户）自动生效
  'Microsoft YaHei UI',  // 未安装则继续往下回退 —— 行为与今天完全一致
  'PingFang SC',
  'Noto Sans CJK SC',
];
```

- 装了该字体的用户 → 编辑器直接用鸿蒙字体（跨平台一致 ✓）
- 没装的用户 → **与今天一模一样**（链首未命中就继续往下 ✓，Flutter 逐字体尝试）
- 想回到今天的状态：删掉这一行即可 ✓

⇒ 这是"**不内置、也不改变现有行为**"的最优过渡方案。

## 6. 落地步骤（若法务确认可内置）

1. 官方设计资源页下载字体包 → 解压，取 `HarmonyOS Sans SC` 的 **Regular** 与 **Semibold** 两个 ttf；
2. `pubspec.yaml` 的 `fonts:` 段登记（family 名如 `'HarmonyOS Sans SC'`，`fontWeight` 400 / 600）；
3. `AppTheme.editorFont` 与 `cjkFontFallback` 指向它，并**保留系统字体兜底**；
4. 第三方许可登记（名称 / 来源 / 版本 / 许可全文）；
5. 实测三平台渲染 + **安装包体积增量**，回归"中英混排基线"与"换行位置"。

## 7. 决策（2026-09-10）

**不内置、也不做软对齐**（保持系统字体）。改为在代码层保证"**按平台统一中英字族**"：

| 平台 | 字族 |
|---|---|
| Windows | `Microsoft YaHei UI`（微软雅黑） |
| macOS / iOS | `PingFang SC`（苹方） |
| Linux 等 | `Noto Sans CJK SC`（思源） |

落点：`AppTheme.editorFont` —— 由常量改为**按 `defaultTargetPlatform` 解析的 getter**。
这同时修掉一个隐患：原先写死 `'Microsoft YaHei UI'`，**macOS 上该字族并不存在**，会导致
英文落到引擎默认字体、只有中文才走回退链 ⇒ **中英不同源**（行内基线会漂）。

一句话：**在"观感收益 / 安装包体积 / 许可风险"三者间权衡后，选择「系统字体 + 按平台同源」**。
将来若确实需要跨平台像素级一致，再回到 §6 的内置流程（**前提是许可确认**）。
