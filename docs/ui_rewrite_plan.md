# UI 重写方案（桌面端骨架优先）

> 定稿 2026-09-21。本文件是**方案登记处**：跨多轮工作，每完成一阶段就把「验收」栏回填。
> 数值基线见 `docs/perf_baseline.md`（阶段 0 产出）。
>
> 一句话：**先立桌面端的物理法则（命令层 + 可寻址定位 + 交互骨架），再做平台适配层，最后才换皮。**

## 0. 三条不可动摇的边界

| # | 边界 | 含义 |
|---|---|---|
| 1 | **数据与内核不重写** | `data/`（store / 迁移 v11 / 检索 / AI）、`canvas/kernel/`、`editor/core/` + vendored editor 全部保留。重写对象只有 `app/`（外壳/面板/浮层）与 `theme/`、各 `*_panel.dart` 的**呈现层** |
| 2 | **每阶段保持测试全绿** | 769 个既有测试 + 架构边界测试是护栏；红了先修再前进 |
| 3 | **换皮最后做** | 外观改动推迟到阶段 4——风险最高的一步，放在测试与数字都就位之后 |

**编辑器内核 UI**（悬浮工具条 / 斜杠菜单 / 块手柄皮肤）是否跟着换皮，**暂缓决定**（见 §12 决策 2）。

## 1. 目标与验收

> **一处定义，四处消费**：每条命令只在注册表里写一次，快捷键 / 命令面板 / 右键菜单 / 工具条都从它取。

| 验收项 | 判据 |
|---|---|
| 命令可键盘到达 | 任取一个现有功能（如"删除笔记"），键盘能到达**且**命令面板能搜到 |
| 注册表自洽 | id 唯一、同作用域键位无冲突、空上下文下 `enabled` 不抛（测试钉住） |
| 悬停不再独占 | §5.5 的 12 处逐条有等价路径，或明确判为可保留 |
| 性能不退化 | 阶段 4 结束时逐场景对比阶段 0 基线（§7） |

## 2. 设计原则（物理法则）

### 2.1 三层约束强度（递减）

| 层 | 内容 | 强度 |
|---|---|---|
| **词汇表** | 间距 / 圆角 / 描边 / 层级 / 状态层 / 动效时长 | 100% 统一，不许例外（`Tokens` 已达标） |
| **语法** | 同一语义 → 同一画法 | 必须统一（当前"当前项"有三种画法，见 §5.1） |
| **修辞** | 强调色出现的场合与频率 | 必须吝啬：一屏最好只响一次 |

### 2.2 三语义判据（强调色的唯一合法用途）

1. **我在哪**（当前项 / 焦点）2. **我能做什么**（主操作）3. **哪里有危险**（错误 / 删除 / 重置）

不沾这三条 ⇒ 完全中性。**判别标准不是"重要不重要"**。

### 2.3 两族表面（并列，不抹平）

| 族 | 成员 | 底色 | 层次手段 |
|---|---|---|---|
| **浮层族** | 菜单 / 气泡 / 工具条 / 斜杠菜单 / 问笔记 / **命令面板** / **设置面板** / **关于面板** | `AppTheme.floatSurface`（纯中性，不染种子色）；**半透档取 `menuFill`**（只给磨砂那几件） | 三件套：底色 + `menuBorder` + `floatShadows`；**模糊 / 玻璃按面积分档**（见下） |
| **面板族** | **许可页**（框架 `LicensePage`，我们不自绘它的表面） | `scheme.surfaceContainerHigh`（M3 内容档） | **遮罩**表达浮起；无阴影、无 tint |

族差是"轻浮层 vs 重面板"的合法差异；**族内语法必须一致**。
📌 **2026-09-22 变更**：设置面板与关于面板从**面板族搬进浮层族**（与主菜单同一批令牌）——
"设置页 / 关于页"本就是短暂浮起的内容面板，而它们原来那档 `surfaceContainerHigh` 带种子色相
（与 §2.1"大面不染种子色"冲突）。面板族因此只剩框架的许可页；详见 §5.6。
⚠️ **族内按"面积 / 是否开模糊"分两档**（2026-09-22 定稿）：

| 档 | 谁 | 底 | 光 / 模糊 |
|---|---|---|---|
| **磨砂** | 主菜单 / 关于面板 | `menuFill`（半透 0.80） | `blur: true`（σ 12） |
| **实色 + 玻璃** | **设置面板**（11% 屏，第二档） | **实色 `floatSurface`** | `glass: true`：内光泽 + 顶沿光边（**纯绘制**，无 `saveLayer`）⇒ 面积大也付得起 |

⇒ 面板的"透"到此为止：**没有模糊托着的半透只会是"清晰字影"**（面积越大越明显），
所以设置面板走实色、玻璃感全交给两层光。想再要"透"的唯一正解是**开模糊**
（代价见 `AppFloatSurface.blur` 的面积分档）。

### 2.4 桌面端公约数（两份指南完全一致，可直接定为骨架）

命令必须有权威面 · 悬停不能是唯一发现路径 · 全键盘可达 + 焦点环 · 五态 ·
窗口状态恢复 · 断点**重排**（非等比放大）· 8pt 网格 · 模态克制 ·
尊重系统设置（深色/强调色/降低透明度/减少动效）· 拖放有反馈且有等价命令

## 3. 命令层（P0）

### 3.1 命令模型

```dart
enum CommandScope { overlay, canvas, editor, note, global }  // 解析优先级：左高右低
enum CommandGroup { file, edit, navigate, view, insert, canvas, ai, app }

class Command {
  final String id;              // 'note.new' —— 稳定 id：快捷键映射、测试、ValueKey 都靠它
  final String title;
  final String? hint;           // 面板里补充说明
  final CommandGroup group;
  final List<KeyBinding> keys;  // 可多套；平台别名（⌘/Ctrl）在阶段 3 展开
  final CommandScope scope;
  final bool Function(CommandContext) enabled;  // ★ 置灰而非隐藏
  final bool dangerous;         // 走 error 语义
  final bool longRunning;       // 见 §3.6
  final Future<void> Function(CommandContext) run;
}
```

| 决策 | 内容 | 理由 |
|---|---|---|
| id 与实现解耦 | 字符串常量，不绑类名 | 换皮时 id 不变 ⇒ 快捷键、肌肉记忆、测试全继承 |
| **置灰而非隐藏** | 不可用时仍显示、灰显并给原因（"需要选中文本"） | HIG 最硬一条：命令永不消失，这是可发现性的来源 |
| **唯一例外** | AI 类命令在 Ollama 未配置时**不进注册表** | "未配置的服务"不是"暂不可用的命令"。此例外要守住，否则会被滥用成"随便隐藏" |

`CommandContext` 由 providers 提供：当前 noteId / 是否有选区 / 当前块 id / 是否画布笔记 / 画布是否有选中对象。

### 3.2 注册表与四个消费面

```
commandRegistryProvider ──┬── ① 快捷键分发（Shortcuts/Actions，按 scope 分层）
                          ├── ② 命令面板（可搜、可置灰显示）
                          ├── ③ 右键菜单（按 scope + 上下文过滤后生成）
                          └── ④ 工具条（保留，但不再是唯一入口）
```

`lib/src/command/`：`model.dart` / `registry.dart` / `bindings.dart` / `palette.dart` + `commands/`（按域分文件：app / note / editor / canvas / ai）。

#### 实际落地与**分发机制修正**（2026-09-21）

文件：`command.dart`（模型，即计划里的 `model.dart`）/ `registry.dart` /
`fuzzy.dart`（面板匹配与排序，纯函数）/ `commands.dart`（注册表装配 + 命令定义；命令还少，
暂一个文件，长到按域分更清楚时再拆 `commands/`）/ `bindings.dart`（快捷键分发器）/
`palette.dart`（面板）。

计划原话是"`Shortcuts`/`Actions`，按 scope 分层"。实现时按 SDK 源码改为
**一个 `HardwareKeyboard.addHandler` + `CommandRegistry.resolve(activeScopes:)`**：

1. **分层要求"每个作用域边界是一个 widget 子树"**——编辑器的边界在 vendored appflowy
   内部（它自带 `Shortcuts`）、画布用 `Focus.onKeyEvent`，应用侧没有可插进去的层级；
2. **`resolve` 已经是同一套语义**（作用域按声明顺序、更深优先）且是纯函数、已被单测钉住。
   同一语义不写两遍。

⚠️ **代价必须记住**：查 SDK 源码（Flutter 3.47.4 `services/hardware_keyboard.dart`）——
先 `_hardwareKeyboard.handleKeyEvent(event)`（跑所有 handler），随后
`_dispatchKeyMessage(...)`（焦点树分发）**照常执行**；且 `addHandler` 的文档明说返回值只影响
add-to-app 场景的 native 传播。**handler 是旁观者，拦不下按键。**

所以"不跟编辑器抢键"只能靠**键位占用图不重叠**（§3.4），并由元测试
`test/command/command_meta_test.dart` 钉住。将来要加与编辑器同键位的命令，必须先解决
"真消费"（焦点树祖先节点 + `KeyEventResult.handled`），别指望 `return`。

**只放能证明的活跃作用域**：`activeCommandScopesProvider` 只给 `global` / `note`（有选中
笔记）/ `canvas`（当前是画布笔记）。**刻意不含 `editor` / `overlay`**——它们需要"焦点在哪"
这个事实，而应用侧没有全局焦点跟踪；宁可少放一个作用域（表现为"该命令快捷键暂不生效"），
也不能凭猜放行（那会让"编辑器内 `Ctrl+B` 是加粗"这类同键不同义失效）。

### 3.3 作用域解析

```
overlay > canvas / editor > note > global
更深作用域有绑定 ⇒ 由它消费，不再冒泡
（例：编辑器内 Ctrl+B = 加粗；列表上 Ctrl+B 保留给侧栏折叠——本方案改用 Ctrl+\，见 §3.4）
```

### 3.5 命令面板规格

| 项 | 规格 |
|---|---|
| 形态 | **浮层族**（`AppFloatSurface`，纯中性零染色） |
| 位置 | 顶部居中，宽 560，最大高 60% |
| 输入 | 实时过滤；**模糊匹配 + 拼音首字母**（`xjbj` → 新建笔记） |
| 键盘 | `↑↓` 选择、`Enter` 执行、`Esc` 关闭、`Tab` 切模式（命令 ⇄ 打开笔记） |
| 行内容 | 图标 + 标题 + 分组 + **右侧键位提示**（无键位显示"无快捷键"⇒ 键位的发现入口） |
| 禁用项 | 置灰 + 原因，**仍可被搜到** |
| 排序 | 最近使用 → 分组 → 字母 |
| 性能 | 列表 `ListView.builder` + `ValueKey(command.id)`；**输入不得重建编辑器**（`select()` + 独立 overlay 子树 + `const` 隔离） |
| 快速打开数据源 | **必须走 SQL 索引**（`blocks` / `chunks_fts`），不做全表内存扫描；必要时 `compute()` |
| P0 不做 | 自定义键位 UI、插件命令、自然语言命令（可接 `ask`，P2） |

#### 面板的实现期发现（2026-09-21）

| 项 | 结论 |
|---|---|
| ↑↓ 的键盘路径 | **不能用 `Shortcuts`**：单行输入框的 `EditableText` 会**消费**方向键去移动光标，焦点树里的祖先节点收不到 ⇒ 用与 Esc 同一个全局旁观者（面板 `initState` 装、`dispose` 摘） |
| Enter | 交给 `TextField.onSubmitted`——单行输入框会消费 Enter 并回调它，于是"回车执行"只有一条路径，不会与旁观者重复触发 |
| 置灰原因 | 复用 `Command.hint`（"先在列表里选一篇笔记"），**不为模型再加字段**：这句话在可用时也是有意义的说明 |
| 拼音首字母 | 自带一张 **26+字** 的表（`fuzzy.dart`），不引拼音依赖；由元测试钉住"注册表里的字都被覆盖"——漏字的后果是"搜不到"，最该被拦住的一类静默退化 |
| id 也参与匹配 | 标题是中文而 id 是 `note.new`：敲 `new` 也该找得到（否则中文用户只有背拼音键一条路） |
| 排序 | 已做"分组 → 标题"；**"最近使用"未做**——半做的排序会让顺序看起来随机，比固定顺序更糟（要有会话级使用记录再做） |
| 面板里的 `DismissIntent` | 必须自己映射：`EditableText` 收到 Esc 会 `Actions.invoke(DismissIntent)` 收触屏工具条，而本应用的 `MaterialApp`（material_ui 实现）**没有这个映射** ⇒ 抛 "Unable to find an action for an Intent with type DismissIntent"（集成测试实测）。**同样的问题存在于问笔记 / 设置面板**（它们的输入框 + Esc 会走同一条路），待修 |
| 单例浮层 | 连按两次快捷键不叠两层（叠了以后 Esc 只关最上面那层，看起来像"Esc 失灵"） |

### 3.6 长任务与错误（统一约定）

`Command.longRunning` 标记 ⇒ 统一反馈通道：进度可取消（沿用 `IndexCancelToken` 模式）、失败给可操作文案（沿用 `LlmUnavailableException.message` 口径）。
**禁止每个命令自己弹一套 UI。**

## 4. 可寻址定位（`locateProvider`）

现状：跳转靠临时通道（`pendingBlockJumpProvider`），是"搜索/反链/角标各修一条路"的症状。改成**唯一导航真相源**：

```
locateProvider : (noteId, blockId?, focus?)     ← 一切跳转都走它
    搜索 / 反链 / 问答角标 / 命令面板 / 会话恢复
```

一次改造拿到三样：deep-link 语义（角标跳块不再是特例）、**状态恢复的落点**（§5.4）、"跳转只此一条路"的可测性。

> **不引入 GoRouter**：桌面单窗口双栏 + 浮层不是页面栈；引入要新增依赖、动 `navigatorKey` 与 12 处 `OverlayPortal`（架构测试守着现状）。借其思想，不取其依赖。

### 4.1 落地（2026-09-21）

`locateProvider` 已接管**全部**跳转入口，临时通道 `pendingBlockJumpProvider` 删除：

```
locate({noteId, blockId?, focus?})  ← 唯一入口
   ├── 列表点击 / 反链面板 / 引用块点击     （换笔记）
   ├── 问答角标                            （换笔记 + 走到块 + 交焦点）
   ├── 新建笔记 / 新建画布后选中            （换笔记 + 交焦点）
   └── 撤销删除 / 删除后自动选下一条        （换笔记）
```

三个实现要点，都是"错了不报错、只会现象诡异"那种：

| 要点 | 为什么 |
|---|---|
| 请求带**单调 `seq`** | 连着点同一条角标两次必须能再跳。只比 `(noteId, blockId)` 的话，第二次是"状态没变"、Riverpod 不通知 ⇒ 现象是"第二次点击没反应" |
| `focus` **默认 false** | 交焦点靠"**设选区**"（vendored 键盘服务在选区变化时 `requestFocus`）。从列表点开一篇若带 `focus`，焦点被抢进编辑器，键盘上下选笔记就断了——所以只有"新建后"与"角标跳原文"带它 |
| 只有它写 `selectedNoteIdProvider` | 由 `test/architecture` 的**源码扫描**钉住（不靠自觉）：`lib/` 里除 `providers.dart` 外出现 `selectedNoteIdProvider.notifier` 即红。唯一例外是"删空笔记后回到空态"——那是清空，不是"跳到哪里" |

编辑器侧的消费仍是"按 `ValueKey(noteId)` 重建 ⇒ initState 消费"，另外加两件事：
`blockId` 存在才滚动 + 闪烁；`focus` 为真才落光标（落目标块行首，目标不是文本块则退回
"首个文本块"，不硬塞一个没有意义的 offset 0）。

## 5. 交互骨架（P1）

### 5.1 五态令牌

`default / hover / pressed / focused / disabled` 一处定义、处处消费（现有 `stateLayer` / `stateLayerPressed` 已有一半）。

#### 「当前项」统一读法（✅ 2026-09-21 落地）

改前有 **10 种**画法（`secondaryContainer` / `activeTint` / `SegmentedButton` 默认 /
主色实心 / 只改字重 / 只加描边 / M3 默认 …）。收敛为**一语义一画法**，并按"形状上
有没有左侧"分成两支——这不是打折扣，是"族内语法一致"的必要条件：

| 类 | 读法 | 成员 |
|---|---|---|
| **A. 列表 / 导航行** | `navSelectedTint` 圆角底 + **3px `navIndicator` 左条** + **w600** | 笔记列表项、目录面板激活项、设置面板左导航 |
| **B. 分段 / 行内选中**（形状上没有"左侧"） | 同上**但无左条** | `SegmentedButton`（明暗 / 正文宽度 / 端点形状）、命令面板行 |
| **C. 已选值 / 已选项**（不是"我在哪"） | 保持各自惯例 | 色板（描边加粗 + 对勾）、下拉菜单当前项（打勾） |

两个语义令牌（**新代码一律用它们**，不要自己挑比例——分叉的根因）：
`AppTheme.navSelectedTint(onSurface)`（= `onSurface @10%`）、
`AppTheme.navIndicator(scheme)`（= `primary`）。

**为什么底是中性、而不是 M3 的 `secondaryContainer`**：种子色用户可换（克莱因蓝 /
绛红 / 蒂芙尼 / 紫罗兰），染色会随种子飘；而"我在哪"的**读法必须恒定**。
指示条取 primary 是因为它是**形状信号**（一根条子）——换种子只换色相、不改读法。

> **与 macOS 的一处有意分歧**：macOS（Big Sur+）的侧栏选中是**强调色填充的圆角块**、
> 没有左指示条。我们选了"中性底 + primary 条"，理由同上：强调色填充的观感随种子色
> 起伏太大，而条子是形状。这条分歧是**决定**，不是遗漏。

**落地时发现的一个真问题**：笔记列表项的**悬浮态与选中态原本同色**（都是纸面色）
⇒ 指针一移上来就分不清"已选"与"正悬停"。现在两态分开：选中 = 中性 tint（三件齐），
悬浮 / 菜单开着 = 纸面色。

> 左条的实现手法：一律走 `foregroundDecoration`（**不占位**）。写进 `border` 会让内容
> 在选中/未选中之间横移 3px——"文字跳一下"是最容易被忽略的粗糙感。

### 5.2 焦点规范

- 统一焦点环（primary 2px + 1px offset）
- **Tab 顺序 = 视觉顺序**
- `Esc` 逐层退出：浮层 → 面板 → 专注模式

#### 落地（🔄 2026-09-21 起，分两步）

**改前的现状（盘点结论）**：全仓**没有任何焦点环**——只有 `TextField` 有
`focusedBorder`（2px primary）；自绘交互件（笔记列表项、标题栏按钮、画布工具条、
块手柄）**既不可键盘聚焦、也没有焦点表达**（`HoverStateLayer` 只看 hover/pressed）。
所以 §5.2 不是"画一个环"，而是"把自绘交互件接进 Focus 树"。

**第一步（✅ 已落地）**：令牌 + 可复用渲染件 + 第一个消费者。

| 件 | 落点 |
|---|---|
| `Tokens.focusRingWidth = 2` | 几何 |
| `AppTheme.focusRing(scheme, borderRadius:)` | 唯一出口（取 `primary`——§2.2 的"我在哪"合法） |
| `FocusRing(focusNode:, borderRadius:, child:)` | `theme/focus_ring.dart`：监听**控件自己的** `FocusNode`，`foregroundDecoration` 画环（**不参与布局**） |
| 消费者 | 设置面板左导航 `_NavTile`（它本来就键盘可达、此前毫无焦点提示） |

**实现期两条修正**：

1. **"1px 外间隙"改为画在边界内侧**：向外画要多占 3px 布局——要么内容位移（列表行
   会跳），要么被父容器裁剪切掉；1px 间隙在 32px 按钮 / 28px 行上收益极小。
2. **焦点变化在帧末结算**（`FocusManager` 防重入）⇒ 监听回调引发的重建落在**下一帧**。
   测试里 `requestFocus()` 后要**多推一帧**，否则断的是"上一帧的环"，表现为
   "环卡住不撤"的**假红**。这是调试出来的（第一版误诊为"祖先探针不可靠"，已纠正）。

**浮层族的一条通则（2026-09-21 用户实报的 bug）**：**Overlay 面板打开时必须自己接管焦点**。

- **Esc 走全局 handler 能兜住，Tab 兜不住**：设置面板的 Esc 一直是好的（全局
  `HardwareKeyboard` handler），所以这个洞没被测出来——但焦点还留在背后（编辑器
  `autoFocus: true`）⇒ 按 Tab 只在前一个作用域里转，现象是"**在面板里按 Tab 毫无反应**"。
- **做法**：显式 `FocusNode` + **帧后 `requestFocus()`**。⚠️ **不要用
  `Focus(autofocus: true)`**：它只在"所属作用域内没有已聚焦节点"时才生效，而面板挂在
  `navigator.overlay` 上、背后的编辑器通常已经占着焦点 ⇒ 不保证生效。
- **边界只能靠 `FocusScope`，`FocusTraversalGroup` 圈不住**（2026-09-21 二次实报后查 SDK）：
  `FocusTraversalPolicy._moveFocus` 取的是 `nearestScope`，再 `_sortAllDescendants(scope, …)`
  **只收该作用域的子孙**，走到末尾按 `traversalEdgeBehavior`（默认 `closedLoop`）绕回**本
  作用域**第一个；`FocusTraversalGroup` 只决定**顺序**。所以浮层要自己包一层 `FocusScope`，
  并让它的作用域节点在打开时接管焦点——作用域节点**不在** Tab 序列里，用普通 `FocusNode`
  接管会多出一格"落在面板本身、没有焦点环的空档"。
- 现状（2026-09-21）：**三个浮层都已闭环，且各有回归闸门**——设置面板（接管焦点 + 陷阱，
  `test/app/settings_panel_test.dart`）、问笔记面板（输入框接管焦点 + 陷阱，
  `test/app/ask_panel_test.dart`）、命令面板（同款，`test/command/command_palette_test.dart`）。
- ⚠️ **锚定浮层 `AppPopover`（16 处）还没圈**：它是"挂在按钮旁的小菜单"，Tab 该不该被圈住
  得先定语义（菜单里 Tab 通常意味着"离开并提交"，与面板不同）——语义定下来再动它，别顺手抄。

**第二步（🔄 待做：列表部分挂起，其余照做）**：铺开到其余控件 + `Tab 顺序 = 视觉顺序`。

- **笔记列表的 Tab 停靠：⏸ 挂起（2026-09-21 用户决定：界面布局即将改）**。它本来是
  本步的卡点：列表项是 `GestureDetector`（不可聚焦），简单地给它加可聚焦性会让 200 篇
  笔记变成 **200 个 Tab 停靠点**；正确做法是 macOS 侧栏那种"**整列表一个 Tab 停靠 +
  列表内 `↑↓` 移动选择**"。但**键盘语义与布局是耦合的**（`↑↓` 的顺序、`Tab` 进出的两端
  都长在布局里）⇒ 布局定稿前实现＝按旧布局写新交互。**顺带把语义裁决也挂起**
  （选择是否＝打开、`Enter` 干什么、`Esc` 回到哪）——说早了会被布局推翻。
- **其余控件（标题栏按钮 / 画布工具条 / 块手柄）：与列表形态无关**，照做。

**第二步进度（2026-09-21）**：

**新抽的共用件：`FocusRingIconButton`**（`theme/focus_ring.dart`）。理由：[FocusRing] 必须跟着

夹成圆（M3 `IconButton` 默认 `CircleBorder`）；方角主题显式传 `radiusSm`。

**窗控按钮为什么不进 Tab 序列**：最小化/最大化/关闭在 Windows 与 macOS 都属**非客户区**，
两个平台的 Tab 顺序都不含它们（Windows 走 `Alt+Space` 系统菜单）。把自绘窗控塞进 Tab
是"和平台不一致"——这条是**决定**，不是漏做。

### 5.3 断点

**以窗口宽度为准**（不是设备类别），采用 **650 / 1100**：

```
< 650      单栏（侧栏可滑出）
650 – 1100 侧栏 + 正文
> 1100     侧栏 + 正文        ← 与既有 wideEnough 阈值一致（note_editor_view_appflowy.dart:1272）
> 1400     可选右栏（反链 / 问笔记 / 画布属性）← 增强条件，不是档位边界
```

⚠️ 1100 是**既有值**（注释写明"阈值随侧栏 320→300 同步下调 20"），改它会让目录耳行为漂移。

### 5.4 状态恢复

窗口位置/尺寸、侧栏折叠态与宽度、选中笔记、滚动位置、画布相机——**统一挂在 `locateProvider` 上**。
判据（HIG）：只恢复"有意义且仍然有效"的状态；文件已删/数据源变化时不盲目恢复。

### 5.6 主页与二级页面（hub / 内容页，2026-09-21 定）

**模型（用户 2026-09-21 明确）**：**切换，不是叠加**——同一时刻**只有一个页面在场**。

| 页面 | 底 | 内容 |
|---|---|---|
| **主页** | **窗口底**（纯色，见下；卡片/板直接坐在它上面） | **Bento 卡片格**（见下） |
| **笔记页** | `contentCanvas`（不透明纸面） | 编辑器 |
| **画布页** | `contentCanvas`（不透明纸面） | 画布 |

⚠️ **不做材质叠加**：切到笔记 / 画布页就是**整块换成纸面**，也不做"半透明卡片叠在窗口底上"
的花样。把"左栏 / 右栏"的**空间**分区，改成**页面**分区（空间分区在 <720 折叠时本来就不成立，
见 `home_screen.dart` 的窄屏分支）。

#### 四条决定

| # | 决定 | 理由 |
|---|---|---|
| 1 | **启动停在主页**；"上次编辑的笔记"以**大卡片入口**呈现（**不直接显示笔记**，点了才进） | 启动时因此**不加载编辑器** ⇒ 冷启动首帧不吃它（见下面的性能账）；主页是"能待的地方"，不是关卡 |
| 2 | 主页是**卡片入口分区**（继续上次 / 最近笔记 / 最近画布 / 新建…），不是一行工具栏 | 继续上次是"默认路"、最近是"零思考路"、搜索是"快路" |
| 3 | **切换，不是叠加**：条件构建，**同一时刻只有一个页面在场**；不用路由栈，**也不用 IndexedStack / Offstage 保留其它页面的子树** | ① 用户明确要"切换过去"、不要材质叠加；② 只有真卸载才有冷启动首帧的收益（§7 可测）；③ 保留子树 = 编辑器始终挂载，与"主页不承载输入"相悖 |
| 4 | **画布同走 hub** | 一致性 + 画布需要全屏（高频重绘挤在分栏里更糟） |

#### 切换带来的代价（**必须先定**，否则阶段 4 会返工）

"真切换" = 离开页面时它的 widget 树**被卸载**。两件事因此从"锦上添花"变成刚需：

1. **§5.4 状态恢复**：滚动位置 / 光标 / 选区 / 画布相机，进出页面都要恢复。现在挂在
   `locateProvider` 上的是**跳转**通道，要确认它能覆盖"进出页面"这条新路径。
2. **⚠️ 撤销栈会不会随卸载丢失**：编辑器的 `EditorState`（含 undo/redo 历史）若只活在
   widget 树里 ⇒ 切走再回来，撤销栈清空，只能靠已落盘的文档恢复。三选一，**必须先定**：

| 方案 | 语义 | 代价 |
|---|---|---|
| **A** `EditorState` 提到 provider（不随卸载） | 撤销跨页面存活 | 要处理"文档被别处改了"与常驻内存 |
| **B** 接受"切走即提交" | 撤销只在本页内有效 | 用户可能觉得"少了点什么"，但语义最干净 |
| **C** `Offstage` 保留子树 | 状态天然保留 | **这就是叠加**，与决定 3 相悖，且首帧收益归零 |

👉 推荐：**B 起步**（与"切换"模型自洽、实现最简），实测有人抱怨再升 A。

#### 窗口底：**纯色**（2026-09-22 **定案**，取代同日那版"微渐变"）

窗口底 = `AppTheme.windowBackground(brightness)`（亮 `#F8F8F6` / 暗 `#171715`，**同一个令牌**）。
⚠️ 2026-09-23 起它由**平台窗口**铺（见下），不再是 `MaterialApp.builder` 里那层自绘。

**全路由共用这一个底色**（主页**内容区**的 6px 缝、笔记页侧栏区都吃到它；⚠️ 主页**导航板**自
2026-09-22 起**铺满左侧**，三方不再留缝，见下）。

**⚡ 2026-09-23：窗口自身改**不透明**（`WindowService.applyWindowBackground`）**

三层里原来最下面那层是**全透明**的（`Color(0x00000000)`），底色靠 Flutter
自绘 ⇒ 只要窗口透明，DWM 就得每帧把**整扇窗与桌面**做一次合成/混合（它不知道我们的内容
其实是实心的）。现在平台窗口的底也设成同一个 `windowBackground`（**不透明**）⇒ 这笔省掉。

| 路线 | 窗口 | 每帧多付什么 |
|---|---|---|
| 不透明窗口（**现在**） | 不透明 | 无（两笔都拿：无全窗混合 + 无自绘底 fill） |
| 透明窗口（2026-09-23 之前） | 透明 | DWM 每帧全窗混合 + 自绘底全屏 fill |
| 回退方案 C（**未启用**，见下） | 不透明 | 只付自绘底那次 fill（第一笔仍拿） |

  `SetWindowCompositionAttribute` + `ACCENT_ENABLE_GRADIENT`（`window_manager.cpp:706`），

### 编辑器正文对比度：**APCA**，两边落在 Lc ±90（2026-09-22 用户定）

**为什么换尺子**：WCAG 的 4.5 / 7 只是**下限**，而且**对深色严重高估**（APCA 官方口径：
WCAG 的 4.5:1 在近黑底上可能实际不可读）。此前纠结"暗色 12.5 还是 13.5:1"越调越没把握，
就是因为那把尺子在深色里失灵 —— 同一个"够读"的观感，两边换算成 WCAG 差一大截：

| | APCA（真正的判据） | 换算成 WCAG（仅作直觉） |
|---|---|---|
| 亮色正文达标 | Lc **+90** | ≈ 9.8:1 |
| 暗色正文达标 | Lc **−86** | ≈ 14.4:1 |

**档位**（APCA 官方）：正文**首选 Lc 90**（≥14px / 400）、**最低 Lc 75**；
**暗色上限约 −90**（初步结论）。背后是**对比恒常性**——过了临界对比，再加对比**不会**更好读。

| | 取值 | 对底 | APCA | 备注 |
|---|---|---|---|---|
| 亮色正文 | `#3A3A3A`（原 `#1A1A1A`） | `#F8F8F6` | **Lc +92** | 与 Notion 同档（其默认 `#37352F`） |
| 暗色正文 | `#DDDDDD`（原 `#D6D6D6`） | `#0C0C0A` | **Lc −86** | ⚠️ 别越过 −90 |
| 界面文字 | `scheme.onSurface`（不动） | 同 | +100 / −88.3 | 短文本小字号，越高越好 |

⚠️ **只收正文**（`AppTheme.editorText`）；界面文字与它分工，见其文档。

**为什么暗色要 14.4:1 这么高**——不是"暗色标准更严"，是**同一把尺子在暗色侧刻度失真**。
同一个 WCAG 数字，两种极性下并不等价（同一套公式实测，两边都取"刚好达标"那端）：

| WCAG | 亮色侧（底 `#F8F8F6`） | 暗色侧（底 `#0C0C0A`） |
|---|---|---|
| **4.5:1**（AA 门槛） | `#727272` → **Lc +69** | `#7A7A7A` → **Lc −31.7** ⚠️ |
| 7:1（AAA） | `#555555` → +81.7 | `#9B9B9B` → −48 |
| 10:1 | `#3E3E3E` → **+90.6**（正文达标） | `#BABABA` → −65（**不够**：低于最低档 75） |
| 14.4:1 | `#252525` → +98 | `#DDDDDD` → **−85.8**（达标） |

⚠️ **暗色侧的 WCAG 4.5:1 只等于 Lc −31.7**——比 APCA"任何文本的绝对最低值"（Lc 30）还低。
这就是 APCA 官方那句"WCAG 的 4.5:1 在近黑底上**可能实际不可读**"的量化版。
机制两条：
1. **`+0.05` 这个常数在暗色侧成了分母主导项**（底的亮度 0.0036 ≪ 0.05）⇒ 公式其实在量
   "字有多亮"，而不是"字与底差多少"：把底调到纯黑，WCAG 也只从 14.4 涨到 15.4（+7%）。
   这个常数出自"约 5% 环境光反射"的推导——**是按亮色极性（纸面）标定的**。
2. **极性的视觉不对称**：浅字压深底会发光（halation），感知对比低于亮度差 ⇒ APCA 为此用了
   **两套指数**（浅底深字 0.56/0.57、深底浅字 0.65/0.62）+ 黑位软夹；WCAG 只有一套公式，
   表达不了这个差异 ⇒ 暗色侧的数字被"撑高"。

⇒ 要同样的观感：**亮色 ≈9.8:1 ↔ 暗色 ≈14.4:1**。以后调暗色正文**别盯 WCAG 数字，盯 Lc**。

#### 全仓体检（2026-09-22）：`test/theme/apca_audit_test.dart`（**表 + 闸门**）

逐对算过"文字/图形 vs 它实际铺的底"。第一版抓出**五处真问题**（此前没人发现）：

⚠️ **半透明必须先叠到底上再算**（`apcaLcBlended`）：直接拿色值算会把淡色当成"不透明的深色"，

**"玻璃"到底由什么构成**（2026-09-22 定的口径）：① 镜面高光 / 顶沿光边；② 厚度（上亮下沉）；
③ **透光 / 折射**。纯绘制（两条渐变）能拿到 ①②、拿不到 ③ ⇒ 得到的是"**釉面 / 抛光玻璃板**"，

📌 值得做的依据：亮色下那半点透本来就几乎看不见（`menuLayerAlpha` 注释里的实测："合成色只差

**磨砂是两个旋钮的配对**（缺一个就白做）：
`AppTheme.menuLayerAlpha = 0.80`（底色半透明）+ `AppTheme.floatBlurSigma = 12`（模糊半径）。
- **α 的下界有机器依据**（体检表"**主菜单Layer 压最坏底**"那一行）：半透明面板必须假设
  **背后是最亮/最暗的内容**（模糊只把它糊开、**不改变亮度**）⇒ 暗色主题取背后白图、亮色主题
  取背后暗图。实测扫描（α → 最坏底上的 `onSurface` Lc）：
  | α | 100% | 95% | 90% | 85% | **80%** | 75% | 70% |
  |---|---|---|---|---|---|---|---|
  | 亮色 | 104 | 97 | 89 | 82 | **75** | 68 | 61 ✗ |
  | 暗色 | −84 | −81 | −77 | −74 | **−70** | −66 | −61 ✗ |
  ⇒ **两侧的下界都是 α ≥ 0.75**（0.70 一起掉线）；现值 **0.80 两边都有余量**（亮 75 / 暗 −70）。
  📌 这张表**跟着暗底走**：底抬得越多，半透明面板压在最亮内容上就越亮 ⇒ 暗色那列越紧
  （`+2` 档时暗色在 0.80 只有 −66，只剩 1 个 Lc）。**改底之后这张表要重扫**。
- 只模糊不降 α ⇒ 模糊被实色盖住（"看不出做了"）；
- 只降 α 不模糊 ⇒ **清晰字影**（就是历史上"发脏"那个观感）。

**性能账（`BackdropFilter` 到底贵不贵）**：
成本 ∝ **面积 × 重绘次数**，不是开关式的"有/没有"。
- 面积：菜单 ≈ 300×400 逻辑 px（@1.25 DPR ≈ **0.19 MP**）vs 全窗口 2560×1440 ≈ 3.7 MP
  ⇒ **约 1/20**；
- 重绘：面板打开期间，只有它所在层重绘时才重算。菜单**自身静态** ⇒ 多数情况只在打开那帧付一次；
  ⚠️ 背后若在滚动/动画（编辑器闪动、画布重绘）则每帧付。
- ⛔ 仓库那条红线针对的是**全屏、压在画布高频重绘面上**的毛玻璃——与"面板那一块"不是一回事。
- **量法（别凭感觉）**：`flutter run --profile` → `F9` 开始采集（`lib/src/dev/frame_probe.dart`）
  → 分别采"菜单开着"与"菜单关着"的 `raster_p90_ms` 对比；要更严格就把 `blur` 改 `false` 再采一遍。
- 闸门：结构上（模糊在不在、底色透不透）有测试；**数字**只能这样实测，`perf_baseline.md` 里没有这项基线。

**其余浮层仍实色**（右键菜单、`AppFloatSurface` 的默认档、浮动工具条、`menuTheme`）——
逐个验证再推广，别一次全开。

**浮层描边的"细"用宽度、不用颜色**（2026-09-22 用户反馈"菜单边框线再细一点"）：
菜单/面板描边改成 **0.5 逻辑 px 发丝**（`Tokens.hairlineWidth`），**颜色对比度不动**（仍 Lc 22）
——细线恰恰**需要更高对比度**来补偿（空间对比敏感度），把 Lc 调低会同时撞上"最低可见线"（15）。
⚠️ **例外**：编辑器**浮动工具条**保持 **1px**——它外高按"38 + 上下各 1px"算，宽度一改就与

`AppTheme.menuBorderColor(outlineVariant, brightness)`，阈值只有一处。

⚠️ **取偏上值**：APCA 档位以 Helvetica/Arial 为基准，**中文笔画更细**，我们正文又是 13px。

**为什么把渐变撤了**（用户实报色带后量化出来的账）：

- 渐变两端 暗 `#0D0C0A → #141310` / 亮 `#F5F4F0 → #FBFAF7`，**只差 6~7 个 8-bit 台阶**。
  铺满全屏对角线（≈2900 逻辑 px）⇒ **每 ~420px 一条**能看见的带。暗色更明显（眼睛对
  近黑区的边界最敏感）。
- **台阶数 = 色带数** ⇒ 只有三条路：**接受色带** / **抖动掉它** / **把台阶压到 1（= 纯色）**。
  这块是**窗口底**、不承载任何信息 ⇒ 取纯色。
- ⛔ **独立噪点层治不了它**（2026-09-22 实测：摘掉噪点色带仍在，加回噪点反而更重）。
  机制上：抖动必须发生在**量化的同一步**；叠在上面的图层是在渐变已被量化成 8-bit 之后
  才混合，改不了台阶本身。
- 📌 **要渐变就得同时抖动**（想回来时的唯一正解）：用 `FragmentShader`（Flutter 侧
  `FragmentShader` 可用；**全仓/SDK 都没有一等的 `dither` 开关**，已核实）在同一个 pass 里
  先算渐变、加**有序抖动**（Bayer / 蓝噪声）再输出 ⇒ 只有一次量化。代价是一个 `.frag`
  资产 + 加载失败时回退纯色。渐变令牌 `AppTheme.windowGradient` 与它的测试（≤10/255）
  都留着，随时可回到这条路上。
- **噪点组件（`noise_texture.dart` + `windowNoiseAlpha` / `windowNoiseGrain`）留着不删**：
  它现在是**纸面噪点**（见上面的小节）用的现成件，只是**不作为消色带的手段**（见上）。
  窗口底那档（暗 3% / 亮 1.5%）当前未挂载，铁律仍是 ≤5%；单色、按 DPR 1:1 运行时生成、
  固定种子、只铺在内容之下（纸面的那处夹在纸色与内容之间）。

其余沿用（本轮不变）：

- **窗口材质不做**（Mica 等，2026-09-22 定案）：三端（Windows / macOS / Linux）观感完全一致，
  也不依赖 DWM 合成是否成功。首帧之前那一小段窗口仍是透明的。
- ⇒ 这条决定让"底不可控"的顾虑消失：底是我们自己的中性色，对比度**完全可控**。
- 噪点的其余设计约束沿用（它现在**不挂载**，留着当"想要颗粒感"的现成件）：
  - 铁律 **≤5%**（暗 3% / 亮 1.5%，`AppTheme.windowNoiseAlpha`，测试钉着）——超过立刻"脏"；
  - 颗粒**单色**且按明暗选白/黑（黑粒在近黑底上看不见）；
  - **按 DPR 1:1 运行时生成、种子固定**（不往仓库放 PNG；固定种子才不会"闪"）；
  - 曾有"只能铺在内容之下"的约束（`Stack` 第一层）⇒ 不透明页面自然盖住它，不给正文添颗粒；
  - 绘制是一次平铺 + `filterQuality.none`，**无 saveLayer、无模糊**（红线不碰）。

#### 底上放什么（**底色不可控时**的规则——保留是为了记住"为什么当初要限制"）

> ⚠️ 背景换成可自控的纯色后，这些限制**已放宽**（标题 / 标签 / 预览随便放；正文仍建议在
> 纸面上读）。下面记录的是"底不可控"时得出的结论，别再把它当成现在的硬约束。



- **短文本可以，大段正文不行**（2026-09-22 **更正**：原定"一律不放正文"过严——Windows
  系统页自己就把标题与列表文字放在窗口底上）。改成**可测**的形式：
  * 窗口底的对比度直接用既有算法判：**`onSurface` / `onSurfaceVariant` 对
    `windowBackground` 都要 ≥ 4.5:1**（已过，闸门见 `test/theme/app_theme_test.dart`）。
  * 所以**标题 / 标签 / 一两行预览可以放在窗口底上**，卡片想显示预览就显示；
    **大段正文仍在内容页**——纸面不透明（这也才是"主页不放输入页面"那条决定的本意：
    "**读写的正文**不在主页"）。
  * **表面两档（2026-09-22 定稿）**：

    | 档 | 令牌 | 暗 / 亮 |
    |---|---|---|
    | 导航**板底** | `AppTheme.boardFill` | 白 4% / 白 55% |
    | 板上交互态（悬停） | `AppTheme.boardFillHover`（**叠在板底上的量**） | 白 8% / 白 75% |
    | 选中 | `primary` @ 12% + 左侧 3px 主色条 | — |

    板底是**白色低 alpha 提亮**，不是灰色中 alpha——白不与下层色相打架，"有板"但
    不"脏"。闸门：`test/app/hub_nav_test.dart`（未选中项必须**显式透明**，不许落到
    surface 的近黑——`Material(color: null)` 的坑）+ `test/theme/app_theme_test.dart`。
  * ⚠️ **否决记录**（别再走回去）：
    ① **灰色板底**（WinUI `LayerFillColorDefault`，`#3A3A3A`@30%）——灰罩在底上显"脏"
    （用户与系统设置并排对比后否决）。**"通透"的秘密是更少的层，不是更好的灰**；但
    **完全没有板底**也不行（用户：导航栏还是需要板底）——两版之间"白 4% 提亮"是定稿
    （`panelLayer` 旧令牌已删）。
    ② 描边 + 半透明小方卡（描边像表单控件，`#222`×0.7 在深色下发闷）。
    ③ 不透明实卡 + 每张投影（**投影只给短暂浮层**，常驻卡一多就是噪音）。
    ④ 全宽行堆叠（一条没有构图的列表页）。
  * 半透明纯色**免费**（每像素一次混合），**模糊才是红线**——Flutter 的 `BackdropFilter`
    （`SaveLayer`）别碰；半透明一律用**带 alpha 的颜色**，不要用 `Opacity` widget
    （那才强制 saveLayer）。
  * **窗口底 = 纯色**（2026-09-22 用户定，取代同日那版微渐变）：`AppTheme.windowBackground`，
    由**平台窗口**铺（不在 Flutter 侧自绘）⇒ 全路由共用一层底，且免掉每帧一次全屏 fill。
- ⛔ **窗口材质不做**（Mica / Acrylic 一律）：材质要求窗口透明 ⇒ 把"不透明窗口"那笔省下的
  成本重新付出去；且底会被壁纸/桌面内容染色，与"底必须中性可控"相悖。设计只需在**纯色底**
  上成立。

#### 背景**档位**的明度序（⚠️ 不是"叠层"，见 2026-09-22 澄清）

**页面是切换的**（同一时刻只有一个页面在场，不叠）。但**一个页面内部**仍有"底"与"浮在底上的
块"两档背景 ⇒ 需要的是**令牌的明度序**，跟"层叠"是两回事：

| 档位 | 用在哪 | 明暗 |
|---|---|---|
| 窗口底 `windowBackground`（**不透明**） | 主页 / 全路由的底 | 最暗 |
| 纸面 `contentCanvas`（**不透明**） | 笔记页 / 画布页的整块底 | 中间 |
| 浮层 `floatSurface` | 菜单 / 面板 / **主页卡片** | 最亮 |

序：**浮层 > 纸面 > 窗口底**（明暗皆然，`computeLuminance`）。主页本身只有一层页面，但它是
"窗口底 + 卡片（浮层档）"两档 ⇒ **卡片必须比窗口底亮**，否则卡片会"陷进去"。
另：`contentCanvas` / `windowBackground` 都必须 `alpha == 0xFF`（否则壁纸从底下透上来）。
闸门：`test/theme/app_theme_test.dart`。

  当天先做过一版**彩色 mesh**、被这一版取代——色带的教训全部沿用）

  观感：**亮色 = 主白纸 + 淡墨晕染；暗色 = 主黑纸 + 亮墨晕染**（同一套数学，只换墨色）。
  "无规则染色" = **fBm 分形噪声（4 octave）+ 域扭曲（domain warp）+ 阈值晕染 + 墨势**
  （域扭曲让等值线弯折勾连，才像墨洇而不是椭圆噪点；"墨势"让水从一处晕开 ⇒ 有主次）。

  | 架构决定 | 理由 |
  |---|---|
  | **数学全在 Dart**（`nav_ink.dart`），预烘焙成低分辨率 LUT（`ui.Image` 128×512） | GLSL 在测试里编译不了 ⇒ 对比度闸门只能测 Dart；单一事实来源 |
  | **shader 只做"采样 + 抖动"**（`nav_ink.frag`，十几行） | 第一版把噪声写进 GLSL 并用了 **uint 位运算 ⇒ impellerc 直接 SIGABRT**（SkSL 不支持无符号整数，实测踩坑） |
  | 噪声 hash 用**整数运算**（uint32 回绕），别用 sin 大数 | GLSL float32 与 Dart double 对不上 ⇒ sin hash 的镜像会失真；整数 hash 逐位一致 |
  | LUT 的双线性采样 | 顺带把残余台阶平均掉（白赚的减带） |

  ⚠️ **墨是无彩色的（R≈G≈B 暖灰）**——这是水墨比彩色 mesh 好做的地方：灰阶底上明暗
  两种文字都好过档（彩色方案死在紫斑 2.7:1）。**别把墨调成带彩色的**（闸门有专门一条拦）。

  📌 参数与实测（`test/theme/nav_ink_test.dart` 沿整列密采样取最差点 + 验"留白为主"）：
  墨色 亮 `#E3E2DB` / `#CFCEC5`，暗 `#2C2C29` / `#383833`；**平均晕染 ≈ 25%**（留白为主 ✓）；
  最差对比度 亮 **86.0 / 75.1**、暗 **84.3 / 65.5**（门槛 65 / 60 —— 灰阶底余量巨大）。
  🔧 想换花样：改 `NavInk` 的 `offsetX/offsetY`（种子）、`scale`（碎度）、`wash0/wash1`
  （覆盖率）、墨色浓度 —— 改完跑闸门即可。

  ⚠️ **shader 里严禁 uint / 位运算**：SkSL 不支持无符号整数（实测 SIGABRT），
  `test/theme/nav_ink_test.dart` 第一条会拦（"不许把数学搬回 GLSL"）。
  🔧 回退：shader 装载失败 ⇒ `NavInk.painter` 返回 null ⇒ 导航列继续用 `boardFill` 实色，不会白屏。

- ⛔ **窗口材质不做**（2026-09-22 定案，取代原"Mica 计划"）：材质要求窗口透明 ⇒ 把"不透明
  窗口"省下的那笔成本重新付出去；且底色由壁纸决定 ⇒ 导航列的对比度**不可静态界定**。
  **不再作为待办**：导航列就是 `boardFill` / `NavInk` 实色。

## 9. 界面风格重定（**Apple 口径**，2026-09-21 定）

**目标**：Apple 式的**克制与精致**。**不模仿 macOS 的窗口控件与导航范式**——那会变成
"在 Windows 上假装是 Mac"（HIG 自己也不建议跨平台互相模仿）。

判据只用 HIG 里两条**可操作**的：① 层次靠**明度与描边**，不靠阴影与饱和；② 同一语义
只有一种画法（= 本方案 §2.1 的"语法统一"）。

### 9.4 组件库现状与"换库"评估（2026-09-21 调查结论）

| 事实 | 数据 |
|---|---|
| 外壳组件库 | `material_ui`（**官方 Material**，2026 年从框架拆成独立包），43 个文件 |

| 库组件用量 | `IconButton` 49、`SnackBar` 22、`TextButton` 20、`Dialog` 16、`Tooltip` 16、`TextField` 15、`InkWell` 13、`ListTile` 12、`Slider` 9、`SegmentedButton` 7、`Switch` **2**、`Card` **1**；`ElevatedButton`/`Checkbox`/`Radio`/`Chip`/`AppBar` **0** |

**结论**：观感的绝大部分落在**我们自己的主题层与自绘组件**上（上表第三、四行），所以"Apple 化"
走主题层即可（§9.2）；换库的收益不抵其代价——桌面必需的 `MenuAnchor` / `MenuBar` / `PopupMenu` /
`Tooltip` / `SnackBar` / `DataTable` 在 Cupertino 里**缺位或很弱**，且 174+ 文件的编辑器仍在
Material 上（换了会成三套栈，而编辑器是停留最久的界面）。将来若要那几个控件的**手感**
（Switch / Slider / 分段控件），再**局部**引 `cupertino_ui`，不做整体迁移。

编辑器换皮的三种手段（按成本递增，全部已在用）：① **注入槽位**（块组件表 / 工具栏 items /
斜杠菜单 `SelectionMenuStyle` / 浮条 `style`+`decoration` / 右键菜单 builder）；② **替换块组件**
（`custom_block_components.dart`）；③ **vendored 打补丁**并登记 `PATCHES.md`——现成 18 条补丁里
13/14/15 三条就是皮肤性质的，说明这条路通，代价是每次上游升级要重放。
