# 屏幕截图（WeChat 式）设计

目标：实现类微信的截图体验——**全局热键 → 圈选 → 标注 → 复制/保存/钉在桌面**。
状态：**待评审**，未动代码。2026-09-16 立项。

## 一、结论

**这个功能 90% 可以用纯 Dart 完成，不需要先建 Rust 工具链。**

必须的原生能力只有一个：**抓取"别的窗口"的像素**。而这一步用项目**已装**的
`win32 ^6.4.0`（GDI `BitBlt`）就能做——已在本机实测跑通（见第二节）。

所以架构上把它设计成**一个可替换的窄接口**，其余全部留在 Dart：

```
热键 → 抓帧（唯一原生点，可替换实现）→ 遮罩/框选/标注（纯 Flutter）→ 输出
```

Rust（DXGI/WGC）因此变成"换一个实现"，**不是本功能的阻塞项**。

## 二、实测数据（本机，2026-09-16）

用一次性探针跑的真实数字（1707×1067 全屏）：

| 环节 | 耗时 | 备注 |
|---|---|---|
| `BitBlt`（屏幕 DC → 内存 DC） | **37 ms** | 阻塞调用，触发时无动画，可接受 |
| `GetDIBits`（取回 BGRA） | 2 ms | `biHeight` 取负 ⇒ 自上而下，省一次翻转 |
| 拷进 `image` 包 | 41 ms | 本质是 7MB 的拷贝 |
| **全屏 PNG 编码（Dart `image`）** | **95 ms** → 246 KB | |
| 800×600 裁剪 + 编码 | 42 ms → 88 KB | 真实截图多落在这个量级 |

**对照**：同样 1080p 的 PNG 编码，Rust（`png` crate + `Compression::Fast`）为 **16 ms**
⇒ Dart 侧慢约 6 倍。但这是**一次性动作**，95ms 用户感知不到；只有将来做
"连续捕获/录屏"时，这 6 倍才是真问题——那时再换实现。

**抓到的是真画面**：采样 1822/1821 非零，不是黑屏。

### ⚠️ 一个必须解决的实测发现：DPI

探针里 `GetSystemMetrics(SM_CXSCREEN)` 返回 **1707×1067**——这是 **DPI 虚拟化后的
逻辑尺寸**，不是物理像素。也就是说：**现在直接抓，得到的是被缩放过的画面**，
在高 DPI 屏上会糊，多显示器不同缩放时还会错位。

必须先声明 `SetProcessDpiAwarenessContext(PER_MONITOR_AWARE_V2)`（或改应用清单），
再用 `GetSystemMetricsForDpi` / 各显示器真实像素抓取。这一条请在第一版就做掉，
否则后面所有坐标换算（框选、放大镜、多屏）都要返工。

## 四、架构：三层 + 窄接口

```dart
/// 一次抓帧的结果（BGRA，自上而下）。
class CaptureFrame {
  final int width, height;
  final Uint8List bgra;      // stride = width * 4
  final int dpiScalePercent; // 抓取时该显示器的缩放，供坐标换算
}

/// **唯一的原生点**：把"怎么拿到像素"隔离成一个接口。
abstract class ScreenGrabber {
  /// 抓整个虚拟屏幕（多显示器并入），或指定显示器。
  Future<CaptureFrame?> grab({int? monitorIndex});
}
```

- 第一版实现 `GdiGrabber`（`win32` 包，零新依赖）
- 将来加 `DxgiGrabber`（Rust）——**只换这一行，其余代码不动**

分层：

1. **抓取层**（`ScreenGrabber`）— 唯一原生点，输出 `CaptureFrame`
2. **编辑层**（纯 Dart）— 遮罩、框选、标注；复用画布内核
3. **输出层**（纯 Dart）— 剪贴板（已有）/ 文件 / 钉住窗口（多窗口包）

## 五、时序（关键：先抓后弹遮罩）

```
热键 → ① 抓帧（此刻屏幕上还没有我们的 UI）
      → ② 显示全屏遮罩（用第①步的位图当背景）
      → ③ 用户框选 / 标注
      → ④ 裁剪 + 编码 → 剪贴板 / 文件 / 钉住
```

⚠️ **顺序不能反**：任何一个"先弹 UI 再抓"的实现，都会把遮罩自己截进去——
这正是要把抓取独立成一个步骤、而不是混在 UI 里的原因（微信也是先抓全屏再弹层）。

至于 ① 的 37ms 阻塞：触发瞬间界面没有动画，可直接主线程做；
若实测有掉帧，再挪到**长驻 worker isolate**（那也是本项目已经计划做的优化）。

## 六、`win32 6.4.0` 的两个 API 变化（实现时会撞）

1. **句柄不再是 `int`**：`HDC` / `HBITMAP` / `HGDIOBJ` 都是**包装 `Pointer` 的扩展类型**，
   彼此**不自动转换**。混用要显式重建：`SelectObject(memDc, HGDIOBJ(bmp))`。
2. **返回值变 `Win32Result<T>`**：不再是裸 int。取 `.value` 拿 API 返回值，
   `.error` 是 `GetLastError`（0 表示成功）。

## 七、标注层：直接站在画布内核肩上

sinan 已有的 `lib/src/canvas/kernel/` 提供：相机（缩放/平移）、文档（命令栈 + revision）、
笔迹（`perfect_freehand` 的压感轮廓）、命中测试。截图标注需要的正是同一套东西：

- 手绘箭头/圈选 → 笔迹层
- 矩形/椭圆/马赛克 → `CanvasItem`
- 撤销/重做 → 命令栈
- 显示列表缓存（`committedPicture`）→ 标注多了也不卡

⇒ 截图不是"另起一套编辑器"，而是**画布内核的第二个消费者**。这是用 Flutter 做这一层的
最大收益，也是 Rust 方案给不了的（它只负责取像素）。

## 八、暂不做 / 待定

- ❌ **不做窗口/控件级自动识别**（`EnumWindows` + 自动吸附边框）——微信有，但价值/复杂度比不高
- ❌ **不做滚动长截图**——需要拼接与去重，另立议题
- ❌ **不做录屏**
- ⏳ **OCR 待定**：先有截图，再决定要不要接 Ollama 视觉模型
