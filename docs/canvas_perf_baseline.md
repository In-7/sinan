# 画布性能基线（2026-09-19 首次实测）

> 复现：`flutter test test/canvas/canvas_perf_bench_test.dart`
> （纯 Dart 测量，不 pump widget；取 7 次中位数，预热 1 次）

## 为什么要做这个

`canvas_architecture.md` 的性能阶梯里，L2（瓦片重放）与 L3（空间索引）都写着
"笔迹 > 1w 条且 L1 不够时再做"。但仓库里**从没有任何实测数字** ⇒ 那两个"该不该做"
一直是悬空的决策。本文件就是把它变成**有据**的决策。

⚠️ 绝对数字随机器变化；**看趋势与量级**（对照 16.7ms 的 60fps 帧预算）。

## 一、笔迹（视口 1600×1000，中位数）

| 笔迹数 | 落一笔后**重录** | 单帧重绘（走 Picture） | 单帧重绘（逐条画，对照） |
|---:|---:|---:|---:|
| 1 000 | 0.93ms | 45μs | 389μs |
| 4 000 | 1.6ms | 167μs | 1.6ms |
| 10 000 | 4.4ms | **383μs** | 4.2ms |

**读出来的三件事**：

1. **重录成本随笔迹数线性增长**（0.93 → 1.6 → 4.4ms）。因为每落一笔 ⇒
   `document.revision` 变 ⇒ `pictureFor` **重录全量 Picture**。所以写满 N 笔的总
   代价是 **O(N²)**——这是 L1 已知的代价，现在有数了。
2. **平移 / 缩放的单帧重绘与笔迹数基本无关**（1w 条只要 383μs = 帧预算的 2.3%），
   且比逐条画快 **11 倍** ⇒ **L1 的 Picture 缓存是有效的，别动它**。
3. 先撞墙的不是帧率，而是**落一笔的重录**：1w 条时 4.4ms（一次性，不是每帧）。

## 二、item（视口同上）

| item 数 | `itemsIn` 扫描 | 绘制（正常缩放） | 绘制（缩到 5%，LOD 生效） |
|---:|---:|---:|---:|
| 100 | 6μs | 89μs | 249μs（关 LOD：502μs） |
| 1 000 | 61μs | 314μs | 1.9ms（关 LOD：3.8ms） |
| 3 000 | **93μs** | 148μs | **3.0ms（关 LOD：10.2ms）** |

**读出来的两件事**：

1. **`itemsIn` 的线性扫描可以忽略**：3000 个 item 只要 93μs。维护一棵空间索引的
   成本（增删/拖动/撤销都要同步）远超这点收益。
2. **LOD 是真省**：缩小到 5%（视口包住整张画布 ⇒ 裁剪失效、全部进绘制）时，
   3000 个 item 从 **10.2ms 降到 3.0ms**，省了 **70%**；关掉 LOD 则吃掉 61% 的帧预算。

## 三、据此做出的决策

| 议题 | 结论 | 依据 |
|---|---|---|
| **item 侧空间索引** | ❌ **不做** | 3000 个 item 的视口扫描仅 93μs；真出问题的"缩小 + 全量可见"已由 LOD 压到 3.0ms。架构上 item 本就是"少量大对象"，线性扫描比索引维护便宜 |
| **笔迹 L2（瓦片重放）+ L3（空间索引）** | ⬜ **暂不做**，但**触发条件改了** | 1w 条时单帧仅 383μs、落笔增量 4.4ms，都在预算内 ⇒ 还不到动手的时候 |
| **新的触发阈值** | **约 2 万条笔迹** | 不是拍脑袋的"1w"。按**先撞墙的那一项**（落一笔的重录）外推：4.5ms@1w ⇒ 约 1.8~2w 条时单次落笔 ≈ 8ms（半帧），书写会开始发涩 |
| **到 2w 条时先做哪个** | **两代缓存**，不是瓦片重放 | 见下节 |
| **下一步（比优化更该做）** | 把"10k stroke 帧率实测"这条从 ⬜ 划掉 | 已由 `canvas_perf_bench_test.dart` 覆盖；每次改绘制管线跑一遍，数字进本文件的"历史"小节 |

### 两代缓存 vs 瓦片重放（到 2w 条时的选择题）

两者解决的是**同一件事**："落一笔就要重录全量 Picture"（实测 4.5ms@1w，O(N²) 的根源）。

| | **两代缓存**（推荐先做） | **瓦片重放**（L2） |
|---|---|---|
| 做法 | `old` = 冻结大图 + `recent` = 最近 K 条（如 200）；每落一笔只重录 `recent`；每积累 K 条把 `recent` 合并进 `old` | world 网格分瓦片，每瓦片一张 Picture；落一笔只重录该笔覆盖到的瓦片 |
| 工作量 | **~40 行**，无空间结构 | 150–200 行新文件 + 改 `pictureFor` / `InkPainter` + 失效策略 |
| 落笔重录 | O(K) ≈ 0.1ms ＋ 摊还 O(N)/K ≈ 22μs ⇒ **~0.12ms（约 35 倍）** | O(该瓦片内笔迹数)，量级相当 |
| 单帧重绘 | 385μs → ~400μs（多一次 `drawPicture`） | 385μs → 只画可见瓦片，但调用次数变多，**可能反而略升** |
| 主要风险 | 几乎无：只有两个对象，不存在"漏标脏" | **中**：漏一处失效 = 缺墨 / 留着已删的墨 —— 可见的正确性 bug，且只在特定操作序列下复现 |
| 顺带收益 | 无 | 笔迹的视口裁剪 —— 但实测单帧本就只要 385μs，**不痛** |

**结论**：瓦片的主业（单帧只画可见部分）在我们的数字里**根本不是瓶颈**；它降低重录只是
顺带，而两代缓存用约 1/5 的成本拿到几乎同样的重录收益。所以顺序定为：

1. **现在**——不做（1w 条还很宽裕，有实测为据）
2. **~2w 条**——先上**两代缓存**（K 可调，用本基准验证收益）
3. **10w 条量级**——两代还不够时，再上**瓦片重放**

> 将来真做瓦片时，失效策略建议：**不要**增量维护笔迹↔瓦片归属，而是
> "revision 变化时 diff 一遍笔迹 id"——O(N) 遍历只花微秒，相比 4.5ms 的绘制可忽略，
> 换来的是**永远精确**知道哪些 id 变了，因此不可能漏标脏。

## 四、怎么用

- 改了 `InkPainter` / `ItemPainter` / `CanvasDocument` 的绘制或裁剪路径 ⇒
  `flutter test test/canvas/canvas_perf_bench_test.dart`，看数字有没有量级退化
  （测试里有一条**很松**的护栏断言，专门抓"把 Picture 缓存去掉""让 LOD 失效"这类退化）。
- 数字有明显变化 ⇒ 更新本文件的表格，并在"历史"里记一笔。
